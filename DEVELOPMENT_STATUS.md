# Entwicklungsstand vor dem ersten GitHub-Upload

Status: 2026-11-07. Version 4.18.23. COD4X CONTROL / COD4X Administration Tool is still in development. Block 18 (remote Linux over SSH) is implemented from the design in docs/superpowers/specs/2026-11-07-remote-linux-ssh-design.md with TDD: a CONTROL PC installs, updates, starts, stops, restarts, reads logs and health of, configures, backs up and restores CoD4x servers on a Linux machine over SSH, agentless (ssh2, SFTP and a fixed command list), key-only login from the vault, host key pinned only after the exact SHA-256 value was confirmed, a changed key stops before any login, never as root. RCON, console, B3, master status, monitoring and the phone gateway are not available for remote servers yet (REMOTE_RCON_UNSUPPORTED / REMOTE_B3_UNSUPPORTED). Block 17 (multi-server isolation, 4.18.22) is unchanged. Open: the native remote check against a real sshd and a real core (scripts/verify-4.18.23-remote-linux-native.mjs, not run yet; it also settles whether /proc is readable over real SFTP), the native three-core check of 4.18.22, and the manual items in docs/WSL-NATIVE-CHECKLIST.md.

Last run (cloud container, Linux, Node 22, non-root user, umask 022): node scripts/preflight-4.18.23.mjs exit 0 (remote Linux gate: 152 tests, 0 skipped); full suite node --test "test/*.test.mjs" 679 tests: 672 PASS / 0 FAIL / 7 SKIP. Run as root, five existing tests fail ("Dedicated runtime must not run as root"), as before. Under a group-writable umask (0002) the vault refuses its data directory by design; the new remote HTTP test creates its data root with mode 0700 and does not depend on the umask. NOT run: the native remote Linux check (needs a real sshd, a CoD4x Linux core and a base game on the server), the native three-core check of 4.18.22, the Windows 11 run and the WSL COD4X-Test run for 4.18.22 and 4.18.23 (last recorded for 4.18.21: Windows 475 PASS / 0 FAIL / 10 SKIP of 485, WSL 431 PASS / 0 FAIL / 54 SKIP of 485). The native checks of 4.18.15-4.18.22 stay part of the preflight and skip without their prerequisites.

Der verschlüsselte Credential-Service, seine API und Oberfläche sind vorhanden; jede Vault-Sperre bricht einen laufenden Runtime-Credential-Zugriff sofort ab und überschreibt dessen Buffer. RCON-Passwort und (seit 4.18.6) optionaler Master-Token werden bei entsperrtem Tresor in einem gemeinsamen withRuntimeCredentials-Scope kurzlebig als „+set rcon_password“ bzw. „+set sv_authtoken“ an den Dedicated Core übergeben und in Runtime-History, -State und -Ausgabe redigiert; bei gesperrtem Tresor oder fehlendem Eintrag startet der Server ohne diese Werte. Beide sind als Startargument für lokale Prozessinspektion sichtbar (Win32_Process.CommandLine, /proc/<pid>/cmdline) – bekanntes Restrisiko. Das Join-Passwort ist weiterhin nicht an den Core angeschlossen. Keine echten Zugangsdaten für diese unfertige Integration verwenden.

Die Quellkonfiguration unter config/ enthält ausschließlich geprüfte leere/default Projektvorlagen. Für lokale Ausführung COD4X_DATA_ROOT auf ein separates, ignoriertes Datenverzeichnis setzen, z. B. in PowerShell vor dem Backendstart:

```powershell
$env:COD4X_DATA_ROOT = Join-Path (Get-Location) 'data'
npm start
```

Backend-/Auth-/Vault-/Serverdaten, Spielassets, Dedicated-Binaries, Abhängigkeiten, Build-Ausgaben, lokale Testhomes und ältere Arbeitskopien gehören nicht ins Repository. .gitignore schützt nur ungetrackte Dateien; vor jedem Commit auch Änderungen bereits getrackter Konfigurationsdateien prüfen.

Das Originalprojekt und die lokalen Sicherungen bleiben beim GitHub-Upload erhalten. Für Versions- und Architekturregeln gelten die vorhandenen ROADMAP-Dateien.
