# B3 Database (Block 14) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Per-instance B3 MySQL/MariaDB setup: test connection, classify schema, verified backup, migrate (core + opt-in eBc), and run B3 against MySQL once the instance is B3 Ready.

**Architecture:**
- Pure logic lives in `lib/b3-database.mjs`.
- DB I/O goes through a fixed Python helper run with the configured B3 interpreter and PyMySQL (`lib/b3-database-helper.mjs`), with secrets on stdin only.
- The per-instance flow, persistence and audit live in `lib/instance-b3-database-service.mjs`.
- The B3 runtime config, API routes and a React wizard are wired on top.

**Tech Stack:**
- Node ≥ 18 ESM, `node:test`.
- Express 5.
- React 19, with esbuild-rendered UI tests.
- Python 2.7 + PyMySQL 0.10.1 (eBc-B3 @ 9096624).

**Spec:** `docs/superpowers/specs/2026-10-20-b3-database-design.md`

## Global Constraints

- **Version:** 4.18.12. Branch `control-4.18.12`.
- **Language:** code, comments, commits and repo docs in English. Error codes are `UPPER_SNAKE`.
- **Dependencies:** no new npm production dependency.
- **Secrets:** the password and DSN never appear in argv, environment, logs, audit, API responses or runtime output. Password buffers are wiped (`fill(0)`) after use.
- **DSN constraints (eBc-B3 `splitDSN`):**

  | Field | Rule |
  |---|---|
  | host | `^[A-Za-z0-9.-]{1,253}$` |
  | port | integer 1–65535, default 3306 |
  | database | `^[A-Za-z0-9_]{1,64}$` |
  | username | `^[A-Za-z0-9_]{1,32}$` |
  | password | printable ASCII `[\x21-\x7e]`, length 8–128, none of `@ " ; \` |

- **SQL sources:** only the audited eBc-B3 files `b3/sql/mysql/b3.sql` and `b3/sql/mysql/b3-update-ebc.sql`, each checked against its pinned normalized sha256 (CRLF→LF, latin1) immediately before execution.
- **eBc confirmation phrase** (exact): `DROP player_core AND prestige_log`
- **Files:**
  - backups: `<home>/b3/backups/b3-<UTC yyyymmddThhmmssZ>.sql`, mode 0600
  - settings: `<home>/b3/database.json`, mode 0600, atomic write (tmp + rename)
- **Concurrency:** migration is refused while B3 runs (`B3_RUNNING`). One operation per instance at a time (`B3_DATABASE_BUSY`).
- **Tests:** every test is registered in `scripts/preflight-4.18.12.mjs`. Test lists are explicit, not globbed.

## Review Focus

1. **A password containing `@`.** It must be rejected at input with `CREDENTIAL_INVALID`, never stored, and never split wrongly by B3. → Task 1 / Task 4 tests.
2. **A backup that is written but truncated, or whose row count differs.** The migration must abort with `BACKUP_FAILED` before any SQL runs. → Task 5 test `aborts on unverifiable backup`.
3. **A settings or password change after a successful test.** The instance must stop being B3 Ready until it is re-tested. → Task 5 test `settings change clears readiness`, Task 4 hook test.
4. **A helper that hangs, or prints extra lines, non-JSON or a huge output.** This must give a bounded failure (`DB_HELPER_FAILED`) and leave no orphan process. → Task 3 tests.
5. **The vault is locked during migration or B3 start.** Expect `VAULT_LOCKED`. Nothing partial may be written, and `b3.xml` keeps its previous content. → Task 5 and Task 6 tests.

### Task 3: Python DB helper runner

**Files:**
- Modify: `lib/b3-database-helper.mjs`
- Test: `test/b3-database-helper.test.mjs`

**Interfaces:**
- Consumes: `validInterpreterPath` (from b3-dependencies), `classifyDatabaseError`.
- Produces: `runDatabaseHelper({ pythonPath, op: 'probe'|'backup'|'apply', connection, password: Buffer, target?, sqlPath? }, { spawnImpl = spawn, timeoutMs = 120000 }) -> Promise<object>`.
  - `probe` resolves to `{ version, tables: {[name]: string[]} }`.
  - `backup` resolves to `{ path, sha256, tables: {[name]: rowCount} }`.
  - `apply` resolves to `{ statements }`.
  - It rejects with `{ code }`, where `code` is one of:
    - the classified DB codes
    - `DB_HELPER_TIMEOUT`
    - `DB_HELPER_FAILED`
    - `B3_PYTHON_PATH_INVALID`
  - `DATABASE_HELPER` is the Python source string.

**Helper protocol:**
- The helper is launched with `[ '-E', '-c', DATABASE_HELPER ]`, `shell:false`, an empty temporary cwd, env limited to `{PATH, SYSTEMROOT}`, and `windowsHide`.
- The request is written to stdin as one JSON line, and stdin is then closed. stdout is capped at 1 MiB; the process is killed when the cap is exceeded or the timeout fires.
- The helper prints exactly one line: `{"ok":true,...}` or `{"ok":false,"error":{"code":<mysql int|"DRIVER_MISSING"|"HELPER">}}`.
- Driver import follows B3's order: pymysql, then mysql.connector, then MySQLdb. Connect with `connect_timeout=5`, `charset='utf8'`.
- `backup`:
  - Use `SHOW TABLES`; for each table, `SHOW CREATE TABLE` and `SELECT *`.
  - Write a header line `-- COD4X CONTROL B3 backup v1`.
  - For each table, write `-- TABLE <name> ROWS <n>`, then `DROP TABLE IF EXISTS`, the CREATE statement, and batched `INSERT` statements with values escaped through the driver's `escape`/`literal`.
  - Write to `target + '.tmp'` with mode 0600, fsync, then rename to `target`.
- `apply`:
  - Read the file and strip `--` and `/* */` comments, except `/*! ... */` conditionals, which are executed.
  - Split at `;` outside quotes and execute each statement in order.
  - On the first error, return its code and the index of the failed statement.
