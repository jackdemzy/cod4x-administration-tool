# Block 22 – End-to-End-Test (4.18.28) – Umsetzungsplan

Grundlage: Spec `docs/superpowers/specs/2026-11-12-e2e-design.md` (gemergt mit PR #51, main 2484299).
Arbeitsweise Sparvariante: je Task ein Commit und Push; zwischendurch nur die betroffene Testdatei
(als Nicht-Root, `umask 022`); volle Suite und Preflight einmal in Task 8; ein Prüfer am Ende.

Ein Fehler, den die E2E-Tests im Produktcode finden, wird im selben Task behoben: erst der rote
E2E-Schritt als Beleg, dann der kleinste Fix, dann ein gezielter Regressionstest in der passenden
bestehenden Testdatei. Prüfungen werden nie gelockert, um grün zu werden.

## Task 1 – E2E-Test-Core

Dateien: `test/support/e2e-core.mjs` (neu), `test/support/e2e-core-udp.mjs` (neu),
`test/support/fake-cod4x-udp.mjs` (optionale Erweiterung), `test/e2e-core.test.mjs` (neu).

- `buildE2eCore(directory)`: kompiliert per gcc ein C-Programm `cod4x18_dedrun`, das sich wie
  `buildFakeCore` verhält (Argumente ausgeben, `+exec` lesen, warten) und zusätzlich `net_port`,
  `fs_homepath` und das RCON-Passwort aus der `+exec`-Datei liest und dann
  `$COD4X_E2E_NODE e2e-core-udp.mjs --port … --password … --hostname …` als Kind startet.
  Auf SIGTERM/SIGINT beendet der Core das Kind und sich selbst; stirbt der Core hart, beendet sich
  der Responder über eine Elternprozess-Prüfung (`process.ppid` wechselt) selbst.
- `e2e-core-udp.mjs` nutzt `startFakeCod4xServer`. Neue optionale Option `joinable: true`:
  ein OOB-Paket `e2ejoin <name>` fügt einen Spieler hinzu, der in `getstatus` und im RCON-`status`
  erscheint (ohne Option bleibt das Verhalten für alle bestehenden Tests gleich).
- Test: Core direkt starten, `getinfo` antwortet auf `net_port`, RCON `status` mit Passwort,
  `e2ejoin` erscheint in `getstatus`, nach Stop des Cores ist der UDP-Port innerhalb von 2 s frei.
  Ohne gcc oder nicht auf Linux: SKIP mit Grund.

## Task 2 – E2E-Backend-Helfer

Datei: `test/support/e2e-backend.mjs` (neu).

- Startet `installer-server.mjs` wie `security-backend.mjs` (isolierte Datenwurzel, freier Port,
  Desktop-Token, `COD4X_*` aus der Umgebung entfernt), aber mit `restart()` bei gleicher
  Datenwurzel, Login-Initialisierung (`/api/auth/init`), `request(route, body, method)` und
  `assertAlive(step)` (`/api/auth/status` 200 und Prozess lebt; sonst FAIL mit den letzten
  Diagnosezeilen und dem Schrittnamen).
- Aufräumen in `t.after`: alle Instanzen stoppen, Backend beenden, Temp-Ordner löschen.

## Task 3 – E2E-Ablauf

Datei: `test/e2e-flow.test.mjs` (neu). Linux, sonst SKIP.

Schritte, jeder mit `assertAlive`: Install (Core per `/api/runtime/adopt` übernehmen) →
Detect Core (`/api/runtime/preflight`: `core.verified`) → BaseGame (Fixture main/zone,
`baseGame.valid`) → Create Server (`POST /api/instances`) → Config (`PUT …/config`, RCON-Passwort
über `…/credentials/rcon`) → Start → Map (`rcon/command map mp_crash`, danach `serverinfo` zeigt
mp_crash) → RCON (`status`) → Master List (`GET …/master`: kontrollierter Zustand ohne Netz, Code
statt 500) → B3 (`GET …/b3`, `…/b3/start` ohne Python: Code statt 500, Instanz läuft weiter) →
Client Join (`e2ejoin`, `GET …/rcon/online` zeigt den Spieler) → Stop → Restart (gleicher Port,
neue PID). Danach Backend-Neustart: Instanz, Config und Credentials sind noch da, Start klappt.

Erwartetes Risiko: Prozess-Identitätsprüfung oder Ownership-Prüfung lehnt den Test-Core ab. Dann
zuerst klären, ob der echte Core genauso abgelehnt würde (dann Produktfehler, beheben), sonst den
Test-Core näher an den echten bringen.

## Task 4 – Multi-Server

Datei: `test/e2e-multi-server.test.mjs` (neu). Drei Instanzen über HTTP auf Port N, N+1, N+2
(freie aufeinanderfolgende UDP-Ports suchen), je eigenes RCON-Passwort. Prüft: jede antwortet nur
auf ihrem Port, das Passwort von 1 wird von 2 und 3 abgelehnt, Stop von 2 lässt 1 und 3 laufen,
Restart von 2 auf gleichem Port.

## Task 5 – Fehlerfälle

Datei: `test/e2e-failures.test.mjs` (neu). Ein Backend, eine laufende Referenzinstanz; für jeden
der zehn Fälle aus der Spec ein eigenes `test()`-Unterkapitel. Nach jedem Fall: `assertAlive`, die
Referenzinstanz antwortet weiter auf RCON. Erwartete Codes werden aus dem bestehenden Code
übernommen (nicht erfunden); wo es heute keinen sauberen Code gibt, ist das ein Fund (siehe oben).

## Task 6 – Gate und natives Skript

- `scripts/verify-4.18.28-e2e-gate.mjs`: führt `test/e2e-*.test.mjs` mit `node --test` aus,
  wertet TAP aus; Linux mit gcc: jedes SKIP ist FAIL; sonst ausdrücklich
  `SKIP E2E gate needs Linux and gcc`. Letzte Zeile `4.18.28 E2E gate PASS`.
- `scripts/verify-4.18.28-e2e-native.mjs`: derselbe Ablauf mit echtem Core
  (`COD4X_CORE`, `COD4X_BASEGAME`), ohne Voraussetzungen SKIP. Optional `COD4X_E2E_MASTER=1`
  (echter Master, Server muss öffentlich erreichbar sein) und B3, wenn Python 2.7 vorhanden.
