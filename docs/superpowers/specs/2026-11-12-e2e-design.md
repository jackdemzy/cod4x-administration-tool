# Block 22 – End-to-End-Test (Zielversion 4.18.28) – Design

Stand: Entwurf zur Freigabe, 2026-11-12. Grundlage: main 8925ecb (4.18.27), Roadmap Block 22.
Entscheidung Rafiki (Karte 2026-11-12 23:48 UTC): **Backend-E2E + natives Skript**, Sparvariante.

## Ziel

Der Roadmap-Ablauf läuft einmal am Stück gegen den **echten Backend-Prozess**
(`installer-server.mjs`, über HTTP mit Login) statt nur gegen einzelne Module:

Install → Detect Core → BaseGame → Create Server → Config → Start → Map → RCON →
Master List → B3 → Client Join → Stop → Restart

dazu drei Server parallel (Ports N, N+1, N+2) und die zehn absichtlichen Fehlerfälle.
Gate: nach jedem Schritt und jedem Fehlerfall antwortet CONTROL weiter
(`/api/auth/status` 200, Prozess lebt). Gefundene Fehler werden in diesem Block behoben,
jeweils mit Regressionstest.

## Bestandsaufnahme (was es schon gibt)

- `test/runtime-http-integration.test.mjs` und `test/support/security-backend.mjs` starten den
  echten Backend-Prozess isoliert (eigene Datenwurzel, freier Port, Desktop-Token).
- `test/support/loopback-transport.mjs` `buildFakeCore`: kompilierter C-Prozess (gcc), der
  Argumente ausgibt, `+exec` wie der echte Core liest und wartet. Antwortet **nicht** auf UDP.
- `test/support/fake-cod4x-udp.mjs`: UDP-Double für getinfo/getstatus/rcon (status, map, serverinfo,
  pluginInfo), nach `sv_main.c` modelliert.
- Gates je Block (`scripts/verify-4.18.x-*-gate.mjs`) prüfen Teilstrecken in-process;
  native Skripte (`*-native.mjs`) laufen nur mit `COD4X_CORE`/`COD4X_BASEGAME`, sonst SKIP.
- Master List kommt fest von `https://cod4master.cod4x.ovh/serverstatus.json`; B3 braucht
  Python 2.7 + eBc-B3. Beides ist im CI nicht erreichbar.

## Umfang

### 1. E2E-Test-Core (`test/support/e2e-core.mjs`)

Ein kompilierter C-Core (gcc, wie `buildFakeCore`), damit die Prozess-Identitätsprüfung des
Runtime-Managers echt durchläuft. Zusätzlich startet er als Kindprozess einen Node-UDP-Responder
auf `net_port` (aus den Argumenten), der `fake-cod4x-udp.mjs` wiederverwendet; der Node-Pfad kommt
aus einer Umgebungsvariable des Tests. Endet der Core, endet der Responder mit.
„Client Join“ = der Responder meldet nach einem simulierten Join-Paket einen Spieler in
`getstatus`/`status`; geprüft wird, dass CONTROL ihn über `/rcon/online` sieht.

### 2. E2E-Ablauf (`test/e2e-flow.test.mjs`)

Echter Backend-Prozess, Login, dann der Ablauf über die öffentlichen Routen:
Install = Core übernehmen (`/api/runtime/adopt`, kein Download), Detect Core
(`/api/runtime/search`/`preflight`), BaseGame (Struktur-Fixture main/zone), Create Server
(`/api/instances`), Config (`PUT .../config`), Start, Map (`rcon map mp_crash`), RCON (`status`),
Master List, B3, Client Join, Stop, Restart. Ein Neustart des Backends mittendrin prüft, dass der
Zustand übersteht (wie im bestehenden Runtime-HTTP-Test).

Master List und B3 im CI: **ohne neue Test-Hooks im Produktcode**. Geprüft wird der kontrollierte
Zustand ohne Netz bzw. ohne Python (verständlicher Code, keine Abstürze, Instanz läuft weiter).
Der positive Weg ist durch die bestehenden Gates (4.18.6/4.18.7, 4.18.10–4.18.21) und das native
Skript abgedeckt.

### 3. Multi-Server (`test/e2e-multi-server.test.mjs`)

Drei Instanzen über HTTP auf drei aufeinanderfolgenden Ports, je eigenes RCON-Passwort.
Prüft: jede antwortet nur auf eigenem Port, fremdes Passwort abgelehnt, Stop von Server 2 lässt
1 und 3 laufen, Restart von 2 auf gleichem Port.

### 4. Absichtliche Fehlerfälle (`test/e2e-failures.test.mjs`)

| Fall | Erwartung |
|---|---|
| falscher Core (Datei ohne Übernahme/kaputt) | Start verweigert mit Code, kein Prozess |
| fehlende main-Datei | BaseGame-Prüfung schlägt mit Code fehl |
| fehlende zone-Datei | dito |
| falscher Port (belegt / außerhalb) | Anlegen oder Start mit Code verweigert |
| falsches RCON-Passwort | RCON meldet Fehler, keine Sperre von CONTROL |
| fehlender Master Token | Master-Status meldet fehlend, Start bleibt möglich bzw. sauber blockiert |
| falsche DB | B3-DB-Test meldet Fehler mit Code |
| B3 down | B3-Status meldet gestoppt, Server läuft weiter |
| Server crash (Core per SIGKILL) | Status erkennt Absturz, Restart funktioniert |
| Plugin fehlt | Plugin-Status meldet fehlend, kein Absturz |

Nach jedem Fall: Backend antwortet, andere Instanzen unbeeinflusst.

### 5. Gate, natives Skript, Version

- `scripts/verify-4.18.28-e2e-gate.mjs`: führt die drei E2E-Testdateien aus; auf Linux ist SKIP
  ein FAIL (gcc ist auf ubuntu-latest vorhanden), auf Windows/macOS ausdrücklich SKIP.
- `scripts/verify-4.18.28-e2e-native.mjs`: gleicher Ablauf mit echtem `cod4x18_dedrun`
  (`COD4X_CORE`, `COD4X_BASEGAME`), Linux/WSL; ohne Voraussetzungen SKIP. Master List gegen den
  echten Master optional (`COD4X_E2E_MASTER=1`), B3 optional, wenn Python/MySQL da sind.
- `docs/WSL-NATIVE-CHECKLIST.md` bekommt Abschnitt Block 22, inklusive manueller Schritte
  (echter Client-Join mit iw3mp, Windows-Lauf, Installer-Download).
- Version 4.18.28: `package.json`, Preflight `scripts/preflight-4.18.28.mjs` (bindet das neue Gate
  ein), `verify-4.18.28-version/runtime`, BUILD_INFO, CHANGELOG-4.18.28.md, DEVELOPMENT_STATUS.

## Nicht im Umfang

Browser-UI-Test (Playwright), echter Installer-Download im CI, echter Client-Join im CI,
Windows-E2E im CI (der Test-Core ist ein Linux-Binary), neue Test-Hooks im Produktcode.

## Risiken

- Prozess-Identitätsprüfung könnte den Test-Core nicht akzeptieren: dann wird geprüft, was der
  echte Core anders macht, nicht die Prüfung gelockert.
- Laufzeit: Ziel unter 60 s für alle E2E-Dateien zusammen; Ports zufällig, Temp-Ordner je Test.
- Tests als Nicht-Root mit `umask 022` (Runtime verweigert root absichtlich).

volle Suite + Preflight einmal am Ende; höchstens ein Prüfer am Ende; Draft-PR bis CI grün.
